# VAMP `ur10e_rail` codegen recipe (ADR-0005 Phase 2, Phase B)

Reproducible recipe that produces `vamp.ur10e_rail` — the cell's 7-DOF
UR10e-on-rail (+ Robotiq 2F-85) as a compiled VAMP robot module, so the VAMP μ
engine (`scripts/vamp_collision_engine.py`) can run on **real cell geometry**
instead of the Phase-A `ur5` stand-in.

The generated header `ur10e_rail.hh` is committed next to this file; everything
else here is the input + commands to regenerate it.

## Build cricket's `fkcc_gen` (codegen CLI only — no JIT, no python bindings)

`fkcc_gen` depends only on `cricket::cricket`; JIT (LLVM link) and the python
bindings are off to cut RAM/time.

```bash
source ~/miniforge3/etc/profile.d/conda.sh && conda activate cricket
cd ~/ompl_icra_ws/cricket_src
CMAKE_BUILD_PARALLEL_LEVEL=2 cmake -GNinja -Bbuild \
    -DCMAKE_BUILD_TYPE=Release -DCRICKET_BUILD_JIT=OFF -DCRICKET_BUILD_PYTHON=OFF \
    -DCMAKE_PREFIX_PATH="$CONDA_PREFIX" .
cmake --build build --target fkcc_gen -j2      # -> build/fkcc_gen
```

## foam — where the arm+gripper spheres come from

The UR10e arm **and the Robotiq 2F-85 gripper** are already sphere-decomposed
upstream: cricket ships `resources/ur10e/ur_10e_spherized.urdf` (79 spheres, the
same foam output VAMP's authors use). We reuse it verbatim rather than re-running
foam on the UR meshes — same decomposition, zero drift. foam is cloned/pinned
above for provenance and would only be needed to re-spherize meshes from scratch
(recursive submodules + SphereTree/Manifold C++ build); it is **not** on this
recipe's critical path.

## Inputs (in `inputs/`, generated by `gen_inputs.py`)

`gen_inputs.py` (committed here) builds three self-contained inputs:

- **`ur10e_rail_spherized.urdf`** — the shipped spherized UR10e+2F85 with the cell's
  prismatic linear guide spliced in at the base. The movable-joint order pinocchio
  sees becomes `[linear_guide_joint(prismatic), shoulder_pan, shoulder_lift, elbow,
  wrist_1, wrist_2, wrist_3]` == the trajectory-artifact joint order (config[0]=rail).
  Rail geometry (support/rail/carriage boxes → conservative sphere rows, +18 spheres →
  97 total) and dimensions come straight from `ur10e_2f85_linear_robot_macro.xacro`
  (`guide_travel=2.2` → rail limits ±1.1; heights 0.70/0.05/0.03). Visual meshes and
  inertials are stripped (collision spheres are all cricket/pinocchio need). The robot
  is placed at a canonical base (y=0, yaw=0, cell height z=0.70) — see "base frame" below.
- **`ur10e_rail.srdf`** — `robot1_*` `disable_collisions` from
  `multi_robot_moveit_config/config/multi_robot_cell.srdf`, de-prefixed to the
  single-robot link names, plus the new rail adjacencies. This only feeds cricket's
  self-collision (`allowed_link_pairs`) code path; it does **not** affect `fk()` or μ
  (see below), it just lets cricket skip the unreliable 1M-sample self-collision guess.
- **`ur10e_rail.json`** — cricket config: `name=UR10eRail`, `end_effector=robotiq_85_base_link`,
  `resolution=32`, `fk_template.hh` + `ccfk` subtemplate (both copied into `inputs/templates/`).

Regenerate the inputs:

```bash
VAMP_CODEGEN_INPUTS=inputs ~/miniforge3/envs/cricket/bin/python gen_inputs.py
```

## Generate `ur10e_rail.hh`

```bash
cd inputs
~/ompl_icra_ws/cricket_src/build/fkcc_gen ur10e_rail.json    # -> inputs/ur10e_rail.hh
cp inputs/ur10e_rail.hh ../ur10e_rail.hh                     # canonical committed copy
```

Produces `struct UR10eRail` with `dimension=7`, `n_spheres=97`,
`s_m[0]=2.2 / s_a[0]=-1.1` (rail limits ±1.1), joints 1–6 as `[-π,π]` revolutes.

## Register in VAMP and recompile

```bash
cp ur10e_rail.hh ~/ompl_icra_ws/vamp_src/src/impl/vamp/robots/ur10e_rail.hh
# ~/ompl_icra_ws/vamp_src/pyproject.toml, [tool.scikit-build.cmake.define]:
#   VAMP_ROBOT_MODULES="sphere;ur5;panda;fetch;baxter;ur10e_rail"
#   VAMP_ROBOT_STRUCTS="Sphere;UR5;Panda;Fetch;Baxter;UR10eRail"
CMAKE_BUILD_PARALLEL_LEVEL=2 .venv_vamp/bin/python -m pip install --force-reinstall \
    --no-deps ~/ompl_icra_ws/vamp_src
```

The `.hh` filename → the python module name (`vamp.ur10e_rail`); the JSON `name`
(`UR10eRail`) → the C++ struct. Both go in `pyproject.toml` (module list is the
`.hh` stem, struct list is the struct name).

## Two things that de-risked this vs the ADR-0005 estimate

1. **SRDF self-collision curation does not affect our μ.** The μ pipeline uses only
   `fk(q)` (all 97 world-frame spheres) + a cross-robot numpy broadcast; it never
   uses VAMP's self-collision / `allowed_link_pairs`. So a rough or guessed SRDF is
   fine — it only has to let cricket emit a compilable header.
2. **The gripper was already spherized.** cricket's shipped UR10e includes the
   Robotiq 2F-85, so only the rail had to be added.

## Base frame — how one module places both cell robots

`ur10e_rail.fk(q)` returns spheres in the robot's **own** base frame (rail along
local +x, arm yaw 0, base at cell height). The two cell robots differ by a
rigid y-offset **and** an arm-mount yaw (robot1 −π/2, robot2 +π/2) that sits
*between* the prismatic joint and the arm — so a single module + single rigid base
transform cannot reproduce both robots exactly (the rail axis is world-x for both,
independent of the arm yaw). The engine
(`scripts/vamp_collision_engine.py`) therefore folds each robot's mount yaw into the
`shoulder_pan` column of the configuration it feeds (the mount is coaxial with the arm's
first joint) and applies a pure ±0.80 m y-translation. The 18 structural rail spheres are
excluded, and a 2 cm sphere margin keeps the model conservative against the meshes. Verified
against the FCL reference: 0 missing forbidden offsets on the `nominal` and `tower` scenes
(ADR-0005).
